# Grant Studio

Updated 4 November 2026. Current document for Grant Studio's scope, data sources, rules and operation. Status and evidence are in [`PROJECT_STATUS.md`](PROJECT_STATUS.md). The curated directory at **Grants** is a separate feature, documented in [`GRANT_RESOURCES.md`](GRANT_RESOURCES.md).

## What it does

Grant Studio helps nonprofits and businesses take a federal grant from discovery to a reviewed, approved application package:

1. **Organizations.** Profiles for 501(c)(3) nonprofits, other nonprofits, small businesses and other for-profits: mission, focus areas, state, annual budget and the most cost share the organization can commit.
2. **Fact library.** Reusable, sourced facts in nine categories: community need, programs, outcomes, history, staff, partners, finances, evaluation and other. Each fact has a label, the statement, its source and an "as of" date. A person confirms each fact against its source, and editing it withdraws the confirmation. Only confirmed facts reach drafting: up to 25 per section (8,000 characters), the section's own categories first (for example, community need for the Statement of need). The Write step lists a section's confirmed facts with **Copy**. In demo mode, the draft outline lists them.
   **Saved writing.** An approved section (never demo text) can be saved to the organization's library with **Save to library**. In a later application, **Reuse approved writing** beside the editor lists the saved texts for the same section, with **Show all** for the others. **Replace** or **Append** inserts one into the section, which reopens it like any edit, so it must be reviewed and approved again. Drafting also receives up to two saved texts for the same section as approved material to adapt. Saved writing outlives the application it came from and is deleted with the organization.
   **Place designations.** The organization's location (street address, 11-digit census tract GEOID and 5-digit county FIPS code) and six place-based designations that funders use for eligibility or priority points: Qualified Opportunity Zone, HUBZone, HUD Qualified Census Tract, HUD Difficult Development Area, persistent-poverty county and USDA rural area. Each designation links to the agency's own lookup tool and its primary sources, with guidance on what to check (see Data sources). Grant Studio does not decide a designation. A person checks the tool and records **In one**, **Not in one** or **Not checked**, the location checked, the tract, county or ZCTA, the date checked (required, never in the future), an optional end date and a note. The person's name is stored with it. A designation past its end date counts as not checked. A result more than a year old is marked **Recheck**.
3. **Readiness.** The registrations and documents funders require, each with a status, an expiry date and a note: SAM.gov registration and UEI, a Grants.gov Authorized Organization Representative, the IRS determination letter (501(c)(3)), financial statements, a board list (nonprofits), a capability statement (businesses) and an indirect cost rate agreement. Matches flag a registration that expires before the closing date.
4. **Matches.** Every open and forecast Grants.gov opportunity, refreshed daily, ranked against each organization. Hard exclusions come first, and each one gives its reason: status, a passed deadline, eligibility type, or cost sharing the organization cannot commit. Then a 0–100 fit score, where every point traces to a stated reason: eligibility, focus areas, distinctive mission words, award size against budget, time to the deadline, readiness, and 5 points when the notice mentions a place designation the organization recorded as in. Each designation a notice mentions (in its title, description or eligibility text) is named with what the organization recorded: a reason when it is in one, otherwise a prompt to check how the notice uses it, or to record it. A notice's mention of "rural" communities alone does not count: only explicit rural-eligibility language does (USDA Rural Development, an "eligible rural area", a rural area "as defined", RUCA codes). **Only my topics** (on by default when the profile has focus areas or a mission) hides eligible but off-topic opportunities. Both counts stay visible. A focus area found in more than 40% of eligible opportunities (judged once there are at least 50) is named as too broad, with a prompt to add specific areas.
5. **Alerts.** An opportunity stored after the organization was added, or after its matches were last marked seen, is **New**. The Grant Studio page shows each organization's new on-topic matches, and those closing within 14 days. The Matches tab adds **Only new**, a closing-soon notice and **Mark all as seen**. After each daily refresh, every organization with new on-topic matches gets one `grant.new_matches` webhook event (see [`automation-api.md`](automation-api.md)). Subscribe in **Settings → Automation** and route it to email, Slack or a CRM with any webhook tool. **Deadlines:** an application, or an opportunity, can be added to a calendar (`.ics`, an all-day event with reminders 14, 7 and 2 days before, and a note to confirm the closing time in the notice). **Deadline calendar** on the Grant Studio page downloads every open application in one file. After each refresh, an application that is not yet exported gets one `grant.deadline_approaching` event as its closing date crosses 14, 7 and 2 days.
6. **Opportunity.** The official record (award range, cost sharing, who can apply, description, assistance listings), the organization's fit, and a link to the official listing.
7. **Application workspace.** Five steps:
   - **Requirements.** A compliance matrix seeded from the application's template (below) and, for federal templates, the common federal forms (SF-424, SF-424A, Project/Performance Site, SF-LLL). The user attaches the notice PDF (see **Notice PDF and requirement checklist** below), or pastes the notice text to extract further requirements with AI, then adds, edits, confirms or rejects rows. Each confirmation records who made it.
   - **Write.** Each section shows its guidance, word, character or page limit and mapped requirements. Users write in the rich editor, can **Draft with AI** (it uses only the organization's facts and marks anything missing as `[Add: …]`), **Review** (score and notes) and **Approve**. Editing an approved section reopens it. **Writing checks** beside each written section, all automatic estimates that help a person review: Flesch-Kincaid reading grade and reading ease, sentences over 35 words, placeholders left to fill (`[Add: …]`, `[Insert …]`, `TBD`, `XX`, `???`), and for objectives sections a SMART check of each objective (a number, a time frame, and a baseline when it promises a change). The **Logic model builder** on a logic model section records inputs, activities, outputs, short-term, intermediate and long-term outcomes, and assumptions, lists what is missing, and puts the model into the section as a heading and a list per column (**Put it in this section** or **Add at the end**), which reopens it for review. Drafting, review and requirement extraction run as background jobs ([`BACKGROUND_JOBS.md`](BACKGROUND_JOBS.md)): a slow provider never holds the page, the section shows the work in progress (even after a reload), and the result appears by itself.
   - **Budget.** Lines in SF-424A categories with quantity, unit cost, match percentage and justification; an indirect rate applied to requested direct costs; the award-ceiling check; and an AI-drafted budget justification.
   - **Format & letters.** The notice's format: font (six common choices), size, line spacing, margins, the narrative page limit and the package file name. Page limits on sections and the narrative estimate follow it (about 500 words a page at Times New Roman 12 pt, single spaced, 1-inch margins, the default), and the exported DOCX uses it. The file name is checked against Grants.gov's default attachment rules: at most 50 characters and only the characters Grants.gov accepts, with a caution for spaces and symbols that some agencies refuse ([Grants.gov Applicant FAQs](https://www.grants.gov/applicants/applicant-faqs)). Without a recorded name, the package gets a Grants.gov-safe name. **Letters of support** tracks each letter: the person, organization, email, what it should cover, the requirement it answers and the due date, with status To request, Requested, Received or Declined. **Copy request** gives a request template built only from what the user entered, with `[Add: …]` for the rest; **Email** opens it in the user's mail program. Grant Studio sends no email.
   - **Review & package.** Eleven compliance checks, or up to thirteen, each with a **Fix** link. No placeholders may remain in any section. When a format is recorded, the narrative must fit its page limit and the file name must follow the rules. When letters are tracked, each must be received or declined. The authorized representative approves the package, which unlocks the final DOCX. A labelled draft DOCX is available at any time.

**Notice PDF and requirement checklist** (`GRANT_PLATFORM_PLAN.md` §6, item 1). On the Requirements step, a writer attaches the funding notice as a PDF: an upload, a fetch from the opportunity's official link, or a fetch from a link they paste. One notice per application; attaching another replaces it.
- **Limits.** Up to 25 MB and 200 pages by default (`NOTICE_PDF_MAX_MB`, `NOTICE_PDF_MAX_PAGES`; hard ceilings 50 MB, the same as source uploads, and 400 pages). Pages past the cap are not read, and the notice says so. The file must start with `%PDF-`. A link must be `https`, without a user name or password, and resolve only to public addresses; the download connects to the address that was checked (the webhook delivery protection in `lib/webhooks/urlSafety.ts`), follows at most 3 redirects, each checked again, and stops as soon as it passes the size limit. An official link is often a listing page rather than the PDF: the notice then says the link returned a web page, and the person downloads the PDF and attaches it. The file is kept in source storage (`SOURCE_UPLOAD_DIR`) and deleted with the notice, the application or the organization.
- **Reading.** A background job (`grant_notice_checklist`, `BACKGROUND_JOBS.md`) reads the text one page at a time with [pdf.js](https://github.com/mozilla/pdf.js) (`pdfjs-dist`, Apache-2.0), in process, and releases each page after reading it. When `DOCLING_SERVE_URL` points at a [Docling](https://github.com/docling-project/docling) service ([docling-serve](https://github.com/docling-project/docling-serve), MIT), it is used first, over HTTP, with OCR off; if it fails, pdf.js reads the file and the notice records why. No OCR: a scanned notice without a text layer is reported as such, and its requirements are added by hand. The page shows the stage and the page reached while it runs.
- **Proposing.** The pages, each marked with its number, go to the configured AI provider (several requests for a long notice). Each proposed row must name its page and quote the notice's words on it. A row is kept only if its page exists and the quotation is on that page (it may run onto the next page; an ellipsis may skip words); points are kept only when the quote states the number. Everything else is dropped, and the notice reports how many rows were dropped. Without an AI key, rows come from labelled pattern matching on the notice's sentences (limits, points, deadlines, attachments, eligibility, forms, formatting), never from the demo model, under the same validation, and both the notice and each row say so.
- **Review.** Every row joins the compliance matrix **proposed**: unconfirmed, with its page, the quotation and who proposed it (`ai:<provider>` or `demo_rules`). The person opens the cited page's text (with the quotation highlighted) or the PDF at that page, then confirms, edits or rejects each row. A confirmation records the person's name and time; **Confirm all** confirms only the rows in the matrix. A rejected row leaves the matrix, the checks, drafting and the package, but is kept with who rejected it and can be restored. **Read again** (for example after adding an AI key) replaces only the proposals nobody acted on; confirmed and rejected rows stay, and a proposal that repeats one of them is not added. **Remove** deletes the notice, its file and its untouched proposals; confirmed rows stay.

**Templates.** A template is the list of sections (title, guidance, limit) and requirements an application starts with. **Grant Studio → Templates** lists them.
- **Built-in templates** ship with the product and are read only: federal nonprofit, federal business, SBIR/STTR, state nonprofit and state business.
- **Workspace templates** are made with **Duplicate** (from any template) or **New template**. People with `grants.write` edit the name, sections and requirements, add and reorder sections, link requirements to sections, and archive or restore them. The server validates every save and lists every problem with where it is (for example "Section 3: the limit must be a whole number"). A save made from an older version is refused rather than overwriting someone else's change, and every save adds a version.
- **Choosing a template.** Each workspace template says when to use it: the organization type, federal or state programs, and optionally text the opportunity title contains. A new application starts from the most specific active workspace template whose rules fit, newest first on a tie, and otherwise from the built-in choice. **Start application** also lets the person pick any active template.
- **Snapshots.** An application copies its template's sections and requirements when it starts, so editing or archiving a template never changes an application already under way. Templates are private to their workspace.

**Competitiveness rating.** Each application shows a 0–100 rating, in the header and on the package step. It rates how ready the application is to compete, not its chance of approval. Four components, each traced to its source:
- **Fit with the opportunity** (25): the match score.
- **Reviewer scores** (35): each section's review score, weighted by the points of the notice's criteria mapped to it, or equally when none are recorded. Unscored and demo sections count as 0.
- **Package completeness** (25): the share of package checks that pass, apart from readiness and the final approval.
- **Registrations and time** (15): 8 points when registrations are ready; up to 7 for time to the deadline.

Bands: Strong (80+), Competitive (60–79), Needs work (40–59), Not ready (below 40), or Not eligible as recorded. **To raise it** lists the actions worth the most points. **Context (not scored)** gives the number of awards at the ceiling that the notice's estimated funding implies (applicant counts are not published) and the organization's own award rate (shown from 5 recorded decisions).

**Calibration.** A calibrated probability of approval needs outcome data, and none is published for these opportunities, so stating one now would be invented: **DEFER**. Instead, the rating and band are frozen when a submission is recorded (and cleared if it is undone). The Grant Studio page then shows the real award rate for each band. A band's rate appears once it has 5 decisions. Owner: product owner; review once 20 decisions are recorded.

**Outcomes and pipeline.** After the final package is downloaded, the Outcome panel on the package step records what happened. Grant Studio never submits, so these are a person's records:
- **Submitted**, with a date and the funder's tracking number. The requested amount is captured at that moment.
- **Awarded** with the awarded amount, **Declined**, or **Withdrawn**, each with a date and a note.

**Undo last step** walks back one step. A recorded submission stops deadline reminders and removes the application from the deadline calendar. Later edits no longer reset the application to draft. The Grant Studio page shows the pipeline: in progress (and due within 30 days), awaiting decision (and total requested), awarded dollars, and the win rate (awarded divided by awarded plus declined).

## Foundations (funding history)

**Grant Studio → Foundations** shows what private foundations have funded, from the grants they report on their IRS tax filings. Every list, profile and suggestion is labelled **"Funding history from tax filings, not an open call"**, and foundation records never count as open opportunities.

- **Search** funders by name, the state they file from, a state they gave in, and a cause (an NTEE major group, A to Y). Results are ranked by giving in that state or to that cause, otherwise by total giving.
- **Profile:** grants paid in total and by tax year, by recipient state and by cause; the grant size distribution (count, median, middle half, smallest and largest); the largest grants to organizations in its latest three tax years with grants; and the source: funder-graph, the dataset version, the latest tax year and period, and the IRS object id of each filing counted. The IRS publishes no web page per filing (funder-graph `docs/research/data-sources.md`), so the profile links to the IRS Form 990 downloads page and to ProPublica Nonprofit Explorer's page for the EIN.
- **Accepts applications.** Each funder shows **Accepts applications**, **Invitation only** or **Unknown**, with the tax year of the filing it came from. It is Form 990-PF Part XIV line 2 (Part XV line 2 on forms before tax year 2022): "only makes contributions to preselected charitable organizations and does not accept unsolicited requests for funds". funder-graph's grant rows do not carry it, so the import reads it from each funder's latest 990-PF e-file XML (`lib/foundations/applicationPolicy.ts`), using the element names in the Nonprofit Open Data Collective's IRS e-file master concordance (`OnlyContriToPreselectedInd`, variable `F9_15_PF_SIOCTPIND`, from the 2013 schemas; `OnlyContributesToPreselected`, `F9_15_PF_SUINONCOTOPR`, in 2009–2012), the map IRSx is built on. **Invitation only** means the box is checked. **Accepts applications** means the filing has its Part XIV and the box is not checked; the profile then shows line 2b–2d as filed (what to send, deadlines, limits on awards; at most 300 characters each, never the contact person's name, phone or email). **Unknown** means no XML was read, the funder files Form 990 (which has no such question) or the filing has no Part XIV. Nothing is guessed. The flag never changes a match score; **Hide funders whose latest filing says they accept no unsolicited requests** filters them out.
- **Matched funders.** For a Grant Studio organization, **Funders matched to your organization** ranks up to 10 funders out of 100 points, from five factors, each shown with its points and the sentence behind them (`lib/foundations/matching.ts`):

  | Factor | Points | Full points when |
  |---|---|---|
  | Gives in your state | 30 | Half or more of its giving went to recipients in the organization's state (fewer points on a square-root scale below that) |
  | Funds your cause | 30 | Half or more of its giving went to the organization's causes: NTEE major groups found in its focus areas and mission, or one chosen on the page |
  | Grant size fits | 20 | With a request amount: the request is inside the funder's middle half of grant sizes (half points inside its smallest-to-largest range). With only the annual budget: its median grant is 2–25% of the budget (half points for 25–50% or 0.5–2%) |
  | Gave recently | 10 | Its latest grants are from the latest tax year in the imported filings (7, 4, then 0 points for each year older) |
  | Gives year after year | 10 | It paid grants in each of its last five tax years (2 points a year) |

  Candidates are the 300 largest in-state givers that also gave to one of the causes. Each match links to its latest filing counted (IRS object id, ProPublica and the IRS e-file downloads) and lists its five most recent filings. Cautions say when causes come mostly from purpose text, that state and cause are counted separately (so the in-state grants may not have been for the cause), and when the funder is invitation only. A match is a starting point for research from funding history: never an open call and never an eligibility decision.

**What is counted.** Only grants paid (`amount_type = paid`; grants approved for future payment overlap later years and are left out, as funder-graph advises). Grants to individuals are excluded and never stored. Grants to recipients of unknown type are counted in the totals but never listed by name. A recipient's EIN, and its NTEE code for the cause, are used only at funder-graph's match confidence 0.90 or higher (`FOUNDATIONS_MIN_CONFIDENCE`, funder-graph's own default). Otherwise the cause comes from words in the grant purpose (shown as approximate), or the grant is not classified. Each tax period is counted from one filing: the latest submitted, so an amended return replaces the original. Private foundations (Form 990-PF Part XV) are imported by default; public charities' Schedule I grants can be added with `FOUNDATIONS_FORM_TYPES=990PF,990`.

**What is stored.** Not the 15.3 million grant rows. The "accepts applications" columns (migration `0034_foundation_matching_past_awards`) add the policy, its filing's object id, tax year and period, and at most 900 characters of line 2b–2d text per funder. For each funder: its totals, giving by year, by state (the 25 largest, the rest as "other"), by cause, how each cause was found, a log-scale size histogram (ten buckets per power of ten, so years merge exactly and percentiles are within about 26%), the filings counted, and its largest recent grants (5 by default). Tables: `foundation_funders`, `foundation_grants`, `foundation_import_runs` (migration `0030_foundation_giving`). Funder records are shared reference data like grant opportunities: every workspace reads the same records and none holds workspace data. Suggestions read an organization only through the workspace that owns it.

**Import.** The `foundation_import` background job (`BACKGROUND_JOBS.md`) reads one filing year at a time, newest first, 10,000 rows at a time, only the columns it needs, with byte-range reads for a remote file. It stops with status `partial` when the foundation tables reach `FOUNDATIONS_MAX_DB_MB`. **It is off on every server until the owner sets `FOUNDATIONS_IMPORT_ENABLED=true`**, because the full import needs more database (and a safer place to run than the 512 MB web instance) than the current plans give: until then the route answers 409, the job refuses to run, and the 30-day schedule is off. Once on, an admin starts it with `POST /api/grants/foundations/import` (admin unlock). Measured size and memory, and what the full import needs, are in [`evidence/foundations/2026-11-05/`](evidence/foundations/2026-11-05/README.md).

**Source and terms.** [funder-graph](https://github.com/egeria-corporation/funder-graph) parses the IRS e-file corpus into a grant edge list. Its code is Apache-2.0, and it states that the dataset derives from US government works. The terms of the hosted copy at `data.opengrants.io` have **not** been reviewed, so the location is a setting (`FOUNDATIONS_DATA_BASE_URL`, an https URL or a local directory) and the pipeline can be run independently under Apache-2.0. Parquet is read with [hyparquet](https://github.com/hyparam/hyparquet) and [hyparquet-compressors](https://github.com/hyparam/hyparquet-compressors) (MIT, pure JavaScript).

## Past federal awards (USAspending)

A federal opportunity's page shows **Past federal awards** for each Assistance Listing (CFDA) number in its Grants.gov record, up to three. From USAspending.gov (`lib/grants/usaspending.ts`), grants only (award types 02–05: block, formula, project and cooperative agreements) whose start date falls in the current federal fiscal year and the three before:

- the number of grants (`spending_by_award_count`), and the 100 most recent (`spending_by_award`, sorted by start date): recipient, amount, fiscal year, recipient state and a link to the award on USAspending;
- the median, middle half and range of those 100 awards, their count by fiscal year and their top states;
- with an organization chosen, how many of them went to recipients in its state, and the latest five.

It is labelled "what this program funded before, not a promise of future awards". State programs and records with no listing number say why there is nothing to show.

**Cache.** A page reads only the `usaspending_award_cache` table (one row per listing: the 100 awards and the count, migration `0034_foundation_matching_past_awards`). The first view of a listing queues a `usaspending_awards` job and waits up to 4 seconds for it; after that, the stored copy is shown, and once it is older than `USASPENDING_TTL_HOURS` (default 168, a week) the page shows it while one refresh is queued. So USAspending is called at most once per listing per week, however many people look. If USAspending cannot be reached, the page keeps the last good copy and says when it was read, or says plainly that the data is unavailable; a failed listing is not tried again for `USASPENDING_RETRY_MINUTES` (default 60). Listings nobody asks for in 90 days are deleted, and at most `USASPENDING_MAX_LISTINGS` (default 500, about 20 KB each) are kept.

**Source and terms.** The USAspending API (`https://api.usaspending.gov`) is public and needs no key; its code and API contracts (`fedspendingtransparency/usaspending-api`) are CC0. The request bodies follow the published contracts. `api.usaspending.gov` was blocked by the build environment's proxy on 6 November 2026 (HTTP 403), so the integration was built and tested against synthetic responses shaped after the contracts, served by a local stand-in. The first live read happens on the server.

## What it does not do

- **It does not submit.** The owner chose assisted submission: Grant Studio prepares and checks the package, and the authorized representative submits it through Grants.gov Workspace (or the funder's portal), confirming the forms listed in that package.
- **It does not decide eligibility.** A match is a guide. Starting an application requires the user to confirm, against the official notice, that the organization meets the eligibility section; the confirmation is stored with the application.
- **It does not decide place designations.** A person records what the agency's tool says; matching only names the designations a notice mentions.
- **It does not invent facts.** Drafting prompts forbid unstated statistics, partners and outcomes, and supply only the organization's profile, its confirmed library facts (each with its source) and the place designations a person recorded as in (with the date checked and the agency). With no AI provider configured, drafting inserts a labelled scaffold, extraction from pasted text is unavailable, a notice PDF gets labelled pattern-matching proposals (each still citing its page) and review runs rule checks only. The package cannot be approved while scaffold text remains.

**Publication gate.** An opportunity is shown only with a title, an `https` official URL, a fetch time, posted or forecast status and, when posted, a closing date that has not passed or a rolling deadline the source states explicitly. The gate is re-evaluated on every sync and detail refresh.

**State programs.** A California record is a state program. Matching excludes an organization recorded in another state, and asks an organization with no state recorded to add one and confirm the program's geography. A stated match percentage is compared with what the organization can commit. A rolling deadline earns time credit and is labelled "Rolling: open until funds run out". Federal registrations (SAM.gov, the Grants.gov representative) are not required for state programs, either in matching or in the readiness compliance check. Applications use the state templates (`state_nonprofit`, `state_business`): the same sections, with state portal and form rows instead of SF-424 and SAM.gov. The package says to confirm forms on the state program's portal.

**Place designations (primary sources, checked 4 November 2026).** Grant Studio stores no designation lists; each one links to the agency's own tool.

| HUBZone | Address (some areas carry an expiration date) | [SBA HUBZone map](https://maps.certify.sba.gov/hubzone/map) and its [help](https://maps.certify.sba.gov/hubzone/map/help) |
| HUD Qualified Census Tract | 2020 census tracts, designated yearly from 1 January | [HUD User QCT/DDA mapping tool](https://www.huduser.gov/portal/sadda/sadda_qct.html); [QCT data](https://www.huduser.gov/portal/datasets/qct.html) |

| USDA rural area | Address, per program | [USDA Income and Property Eligibility](https://eligibility.sc.egov.usda.gov/) |

The tract GEOID comes from the [Census Geocoder](https://geocoding.geo.census.gov/geocoder/). **Automatic lookup: DEFER.** Grant Studio could geocode the address and test each designation's official geography. This build environment's network policy blocks every one of these hosts, so that integration could not be built against real responses or verified. It also needs Render's outbound access confirmed. Recording a person's check is the verified path; revisit once the hosts can be reached (owner: product owner).

## Rules

- Every organization, application and child record is owned by the signed-in operator; another operator's IDs return 404.
- Section HTML is sanitized on the server. AI routes are limited to 40 requests per 10 minutes, and manual sync to 4 per hour.
- Approvals (eligibility, section, package) record who approved and when. Any change to sections, requirements, budget or the format profile withdraws the package approval and returns the application to draft.
- Place designations, the format profile, the logic model and letters are reached only through an organization or application the operator owns; another operator's IDs return 404. An application tracks at most 60 letters.
- The final package is produced only when every compliance check passes and the package is approved. It is generated in memory and streamed with `Cache-Control: no-store`.

## Capacity (measured 4 November 2026)

Production runs on Render's `0.5c-512mb` web instance and `0.1c-256mb` database (`render.yaml`). These figures come from the production build (`node ./dist/index.mjs`) on Linux with Node 22 (Render runs Node 24.15), against PostgreSQL 16 and live Grants.gov and California data. That is not Render itself, so treat them as estimates and re-measure after the first deploy.

| Measure | Result |
|---|---|
| Web process at idle (whole app) | 233 MB resident |
| First sync into an empty database (1,387 Grants.gov records with 1,342 details, then 156 California records) | 89 s; peak 248 MB resident (about 15 MB above idle) |
| Grant tables after that sync (1,543 opportunities) | 4.0 MB; the whole test database was 13 MB. Later syncs update rows in place |
| Matches page for one organization (100 results) | 0.23–0.32 s, 393 KB |
| Grant Studio page with 20 organizations | 2.5 s per load before the summary cache; 2.6 s on the first load and about 15 ms after, with the cache |
| Highest resident memory seen during the matching runs | 294 MB (before the cache); 261 MB with it |

The web instance has about 220 MB of headroom over the observed peak, and grant data adds about 4 MB to the database. The plans fit at this scale. Re-measure if the opportunity count or the number of organizations grows by an order of magnitude. Changing plans is an owner cost decision.

The Grant Studio page's alert summaries are cached in process. The deployment is a single instance, which the runbooks require. An entry is reused until the organization, its readiness, the opportunity store or the date changes.
